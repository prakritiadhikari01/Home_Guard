# HomeGuard

**The backend and web platform of HomeGuard: An Intelligent Home Surveillance System.**

HomeGuard is a Django REST backend, structured with Clean Architecture, that owns users, households, roles, devices, detection events, alerts, and smart-lock state. It also serves the web dashboard and chat assistant. Real-time computer vision is delegated to a separate service, **HomeGuardAI**, so detection models can change without touching permission logic or data persistence, and vice versa.

> Companion repository: [**HomeGuardAI**](https://github.com/prakritiadhikari01/HomeGuardAI) (FastAPI AI engine). The backend runs without it, but detection, face verification, and the assistant require it.

---

## 1. Key Features

- **Home-centric access model**: every Home has an owner and members; permissions are attached to members, not just roles.
- **Role-based access control (RBAC)**: `OWNER`, `ADMIN`, `MEMBER`, `GUEST`, `SECURITY`, each with per-member overridable permission flags.
- **Identity-aware events**: detection events are opened, progressed, and closed by the AI engine; a periodic sweep closes any session left open.
- **Backend-owned alerting**: alerts are evaluated when a session closes, using the person type, time present, and the home's security mode (`NORMAL`, `AWAY`, `HIGH`, `SOS`).
- **Face-verified smart lock (simulated)**: unlocking is an explicit, asynchronous request verified by the AI engine; a recognized face alone never opens the door.
- **Guided face enrollment**: five-pose capture producing one verified face profile per user, reusable across homes.
- **Web dashboard**: security mode, device health, live camera previews, lock status, and recent activity in a single page load.
- **Conversational assistant**: members ask natural-language questions about their home's history; answers are generated by the AI engine from that home's events only.
- **Household isolation**: face matching and data access are scoped per home.

## 2. Roles and Default Permissions

| Role | Control Devices | Manage Members | Unlock Door | Receive Alerts |
|---|---|---|---|---|
| OWNER | Yes | Yes | Yes | Yes |
| ADMIN | Yes | Yes | Yes | Yes |
| MEMBER | No | Yes | Yes | Yes |
| GUEST | No | No | Yes | No |
| SECURITY | No | No | No | Yes |

Owners and admins can override individual permissions for any member. A separate `can_view_dashboard` flag controls dashboard access. The `OWNER` role cannot be assigned through the role-update endpoint.

## 3. Architecture

```
 Browser (dashboard, chat)
        │
        ▼
 Django backend ──► Celery workers ──► HomeGuardAI (FastAPI)
  Interfaces                              detect · track · recognize
  Application                             summarize · assistant
  Domain             ◄── events, clips ───┘
  Infrastructure
        │
   PostgreSQL · Cloudinary
```

Clean Architecture layers:

| Layer | Contents |
|---|---|
| Interfaces | DRF views, serializers, permission classes, URL routing, server-rendered templates |
| Application | Use-case services: Home, HomeMember, HomeInvitation, Device, SmartLock, Enrollment, Dashboard, DetectionEvent |
| Domain | Framework-independent entities, `AccessPolicy`, `EventOrchestrator` |
| Infrastructure | Django ORM models, repositories, signals, `AIClient` |

## 4. Core Workflows

**Detection events.** The AI engine opens an event on the first resolved sighting, sends progress updates while the person is present, and closes it when the person leaves. Closing triggers alert evaluation, after which the engine attaches a clip, thumbnail, and summary.

**Door unlock.**
1. A member requests an unlock; the backend checks that they belong to the home and marks the lock `VERIFYING`.
2. A Celery task asks the AI engine for a one-shot face capture and match against that home's enrolled members.
3. The backend checks `can_unlock_door` for the member who was actually *recognized*, not the one who pressed the button.
4. Success: lock `UNLOCKED`, `DOOR_UNLOCKED` event logged, auto-relock scheduled. Failure: lock stays `LOCKED`, `ACCESS_DENIED` event logged.
5. Each attempt carries a verification ID, so a superseded attempt cannot re-lock a door opened by a newer one.

**Device pairing.** When a smart lock and a camera in the same home share a stream URL, a Django signal pairs them automatically so the lock knows which camera to inspect.

## 5. API Surface Used by the AI Engine

All routes are under `/api/` and require the AI-engine API key.

| Purpose | Method and path |
|---|---|
| Open event | `POST /events/open/` |
| Progress event | `PATCH /events/<id>/progress/` |
| Close event | `PATCH /events/<id>/close/` |
| Enrich event (clip, thumbnail, summary) | `PATCH /events/<id>/enrich/` |
| Upload clip | `PATCH /events/<id>/upload-clip/` |
| Upload thumbnail | `PATCH /events/<id>/upload-thumbnail/` |
| Active cameras | `GET /devices/active/` |
| Enrolled faces for a home | `GET /homes/<home_id>/faces/` |
| Recent events for the assistant | `GET /homes/<home_id>/events/context/` |
| Complete face enrollment | `POST /enrollment/complete/` |

User-facing endpoints (authentication, homes, members, invitations, devices, dashboard, smart lock, assistant) use JWT authentication.

## 6. Data Model

Core entities: `User`, `UserSettings`, `Home`, `HomeSettings`, `HomeMember`, `HomeInvitation`, `FaceProfile`, `EnrollmentSession`, `Device`, `DeviceSettings`, `SmartLock`, `DetectionEvent`, `Alert`, `AccessLog`.

Door attempts are recorded as detection events so that all activity appears on one timeline; `AccessLog` provides a separate, lock-specific audit trail.

## 7. Security

- JWT access/refresh tokens for users; shared-secret API key for the AI engine.
- Sensitive actions are gated by per-member permission flags, not authentication alone.
- Face embeddings are stored per user; matching is scoped per home.
- Permission-update requests are filtered to known keys, so arbitrary fields cannot be injected.
- Password-reset responses do not reveal whether an email is registered; tokens are single-use and time-limited.

## 8. Requirements

- Python 3.10 or newer
- PostgreSQL
- A message broker for Celery (for example Redis)
- A Cloudinary account for media storage
- A running HomeGuardAI service for detection, verification, and the assistant

## 9. Installation

```bash
git clone <repository-url> HomeGuard
cd HomeGuard

python -m venv venv
# Windows:
venv\Scripts\activate
# Linux/macOS:
source venv/bin/activate

pip install -r requirements.txt
```

Create a `.env` file in the repository root (do not commit it) containing, at minimum: the Django secret key and debug flag, database settings, the Celery broker URL, the HomeGuardAI base URL, the shared API key (identical to `API_SECRET_KEY` in HomeGuardAI), and Cloudinary credentials.

Initialize the database:

```bash
python manage.py migrate
python manage.py createsuperuser
```

## 10. Running

```bash
# Web application and API
python manage.py runserver

# Asynchronous tasks (door verification, auto-relock)
celery -A config worker -l info

# Scheduled tasks (stale-session sweep)
celery -A config beat -l info
```

Start HomeGuardAI afterwards. Open `http://localhost:8000` for the dashboard and `http://localhost:8000/admin` for the Django admin.

## 11. Testing

```bash
python manage.py test
```

The test plan covers five categories: functional, integration, end-to-end, security, and negative. Notable cases include role-restricted member management, per-home face isolation, AI-engine API-key enforcement, unlock decisions based on the recognized member, and safe failure when no face or only a low-confidence face is found.

## 12. Limitations

- Detection and recognition quality depend on lighting and on the distance between the person and the phone camera.
- Pre-trained models only; no custom training.
- The smart lock is a software simulation with no physical hardware integration.
- The prototype was demonstrated with a limited number of cameras.
